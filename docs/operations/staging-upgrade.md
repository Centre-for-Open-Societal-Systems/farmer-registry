# Farmer staging: OAN chart install in namespace farmer

Staging runs the same OAN chart as New Dev (`openg2p-farmer-registry` 1.0.0-dev.20, platform
`1.2.2-rc.614`, pinned in `ci/deploy/oan-chart-staging.json`) in namespace `farmer`,
installed fresh beside the legacy release in namespace `far`. The legacy release, its
databases (`*_far`) and its connector are not touched by this pipeline. The earlier
procedure for upgrading that legacy release in place (rc.544, 36 coordinate columns,
baseline hashes) is retired; its contract remains only as `staging-legacy` in
`ci/environments.py` for the retired reset tooling.

Changes land in `develop` and are promoted `develop` to `staging` by PR; see
[merge-develop-staging.md](merge-develop-staging.md). Merging `staging` only validates.

## Contract

| Resource | Staging |
| --- | --- |
| Namespace / release | `farmer` / `farmer-registry` |
| Pin | `ci/deploy/oan-chart-staging.json` (`environment: staging`, chart dev.20 at oan-helm `d7588ad`) |
| Hosts | base domain `oanstaging.com`: `farmer-registry`, `keycloak` (issuer `https://keycloak.oanstaging.com/realms/staff`), `staff-farmer`, `connector-farmer-registry`, `esignet`, `odk-central` |
| Databases | `farmer_registry`, `farmer_registry_idgen`, connector `farmer_connector_v2` |
| Kubeconfig credential / agent | `staging-farmer-kubeconfig` / `vpn-agent2`; API servers `https://10.0.1.212:6443`, `https://52.66.116.220:6443` |
| Overlays | `helm/environments/staging/`: identity, location, outgestion, registrant auth (Fayda), DCI signing |
| Seed | `db_seed` configuration only from openg2p-data; sample, geography and image loaders off; Farmer IDs are generated by the platform |

The owning checks are `ci/environments.py` (`staging`) and `helm/environments/staging/delivery.yaml`.

## Jenkins job parameters

`Gen2-Package/farmer-registry/job/staging`, branch `staging` only.

- `DELIVERY_ACTION`: `validate-only` (default), `fresh-install`, `deploy`.
- `DEPLOY_STAGING` (default false): second guard. Nothing reaches the cluster unless it is
  true **and** the action is not `validate-only`.
- `COORDINATE_SERVICES` (default false): connector and dashboards; only with `deploy`.

Credentials: `staging-farmer-kubeconfig`, `staging-farmer-rehearsal` (evidence file),
and for `fresh-install` the backup target pair `staging-farmer-backup-ssh` (SSH key) and
`staging-farmer-backup-target` (file: line 1 `user@host`, line 2 absolute directory, then the
host's known_hosts lines). These two names are proposed; create them or change the names in
`ci/pipelines/staging.groovy`.

## Before the install

1. Commons on staging is healthy (Keycloak realm `staff` with clients `farmer-registry-staff-portal`,
   `staff-portal`, `openg2p-odk`, `registry-connector`, `registry-connector-ui`; AWE; Master Data with
   the ETH-OAN pack published; Partner Management with `farmer-partner`; consent manager;
   websub; eSignet; MinIO; Redis).
2. Namespace `farmer` exists with `ecr-pull-secret` and a copy of Secret `commons-postgresql`.
3. The pin names oan-helm commit `d7588ad` (chart `1.0.0-dev.20`, platform rc.614; dev stays on dev.19) and
   its `environments/staging/values/farmer.yaml` with sha256 in the `values` block of `oan-chart-staging.json`.
   A newer chart or values file needs a new commit and checksum there (the install refuses empty ones).
4. Evidence: generate the template with `python ci/deploy/staging.py template <file>`, fill it only
   from measured results, bind it as `staging-farmer-rehearsal`. Evidence for this install carries
   `namespace: farmer` and the platform of the pin; it has no baseline revision or baseline hashes.
   Image digests, backup hashes and the freshness rules (24 hours; final backup 1 hour on `deploy`)
   are unchanged.

## Fresh install

Run the staging job with `DELIVERY_ACTION=fresh-install`, `DEPLOY_STAGING=true`. `ci/deploy/fresh-install-staging.sh`:

1. checks the cluster, the pin and the evidence, fetches the pinned environment values (sha256 verified)
   and the chart archive, renders with the OAN renderer and validates the result;
2. dumps `farmer_registry` and `farmer_registry_idgen` with `pg_dump -Fc`, verifies checksums and copies
   them to the backup target, verifying them there. It refuses to continue if a release or a database
   exists and no verified dump was made; a true first install (neither exists) has nothing to dump;
3. uninstalls the release if present, drops the two databases, runs `helm install` with the post-renderer;
4. runs the geography schema gate and the seed metadata checks (`90_checks.sql`) against the new release.

Staging has no automatic Helm rollback. A failed install is diagnosed, then the job is run again.

## Routine deploy

`DELIVERY_ACTION=deploy` upgrades the existing `farmer` release through `ci/deploy/deploy-rc.sh`
with the same OAN renderer, the cutover evidence (maintenance, final backup under one hour) and the
same post-deploy checks. It never installs a missing release.

## db_seed environment

The platform chart's db-seed Job renders no free-form environment, so `registry.dbSeed.envVars`
and `envVarsFrom` never reach it from values. On staging the OAN renderer
(`ci/deploy/oan_compat.py`) adds them to the Job and refuses to override a variable the Job sets.
Dev rendering is unchanged.

## Connector and ODK

Connector values are `helm/environments/staging/services/registry-connector.yaml`: paused at zero
replicas, `farmer-partner` signing with `farmer-connector-v2-staging`, Secrets
`farmer-connector-v2-staging-db` and `-signing` (created by `helm/farmer-connector-credentials`
with `environment: staging`), admin access through `CONNECTOR_ADMIN_AUTH_*` from `adminAuth`. The ODK
Central server is the one inside Commons (`odk-central.oanstaging.com`); the form is rebuilt from the
staging Master Data geography, see [the ODK documentation](../odk/README.md). The connector pipeline
row and handoff (`release_handoff.py --environment staging`) are separate operator steps.
